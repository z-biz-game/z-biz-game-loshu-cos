# 幻方 · LOSHU（填数幻方推理 · 3×3 九宫 / 4×4 四四 / 泛对角）

把 1~n² 各用一次填进方格，让**每一条线**的和都等于同一个数 M。这不是填数字的 Sudoku，
而是一道能整局推到底的算术题：每一行、每一列、对角线的和都必须等于 M = n(n²+1)/2；
泛对角档把对角线换成**闭合的斜带** —— 断开的首尾相接也算同一条线，一共 16 条线
（4 行 + 4 列 + 8 条斜带，主/副对角线就是这 8 条里的两条，不重复计）。

三条硬保证，全部由仓库自带的求解器**现场量出来**，不是写在文案里的：

1. **唯一解**。出货前用穷举复解（第二套实现，逐格比对）确认只有一解；多解的盘直接扔。
2. **不用猜**。每一局都能被六条铅笔规则从头推到尾 —— 一个数都不用试。做不到就重新抽卡，
   所以「卡住了」在本作里不是一个可能的状态（提示永远给得出下一步，除非你已经赢了）。
3. **难度是量出来的**。分数 = Σ规则权重 × 出手次数，是推完这局的实际代价；档位区间是筛子，
   不是标签。下面「难度是量出来的」一节贴的是本机实测输出。

## 快速开始

零运行时依赖：引擎、UI、求解器全是仓库里的纯 JS，`node_modules` 里没有游戏逻辑。
`npm install` 不是必需步骤，也不是任何一步的前提（CI 里同样没有它）。

```bash
npm run check     # 逐文件 node --check（含 server / electron / 测试脚本）
npm test          # 引擎断言 + 现场穷举清点（本机 520 条，~11s）
npm run balance   # 三档各抽 40 局，验证「出货即唯一解、且能推到底、且落在自己区间内」
npm run verify    # 真 headless Chrome：11 个场景 + 窄屏重跑，读 DOM/几何/画布像素
npm start         # http://127.0.0.1:5223/          （npm run dev 同义，显式写端口）
npm run electron  # 桌面壳（唯一的 devDependency 是 electron，只有这条路需要它）
```

`npm run verify` 需要本机的 Chrome：先试 macOS 的两个固定路径（Chrome / Chromium.app），再退到
`PATH` 上的 `google-chrome` / `chromium`，`CHROME_BIN` 可覆盖 —— 所以 Linux runner 上同样能跑。
本仓占 **5223**（web）和 **9373**（CDP）两个端口；被别的进程占着时脚本会等并重试，
不会换端口、不会 kill 别人、也不会为了变绿放宽任何一条断言。

这 339 项浏览器断言在 CI 里跑**两遍**：一遍对着 `server.cjs`（仓库＝文档根），一遍把仓库软链进
一个路径段、用静态服务器端起来 —— 后者才是 GitHub Pages 端这个站点的方式（`…/z-biz-game-loshu-cos/`）。
只跑根形态看不出这一维：兄弟仓 ulam 就这么在已部署站点上少了 19 条根本没跑的断言（`DESIGN.md` 踩过的坑 7）。

## 玩法

- 选档：**九宫** 3×3（M=15，8 条线，留 4 条线索）、**四四** 4×4（M=34，10 条线，留 7）、
  **泛对角** 4×4（M=34，留 6，16 条线 —— 对角线是 8 条闭合斜带，wrap 后首尾相接算同一条）。
- 点格子选中，点下方的数字键落子；键盘 1~9 等价的，`←→↑↓` 移动光标，
  `H` 提示，`Z` 撤销，`N` 切填数/笔记，`Backspace`/`Delete` 擦掉。
- 右侧**线账本**是这局真正的进度：每条线一行读数，合上了写 `15 ✓`，没合上写
  `12 · 差 3（剩 1 格）`。顶部 `Σ线 = n·M = 3×15 = 45 = 1+2+…+9` 是恒等式自检 ——
  所有线的和加起来必须等于全盘数字之和，这条等式一旦不成立，游戏自己就知道哪里错了。
- **笔记模式**下的点子只写在角上，是给你自己看的便签：它不改候选、不改线账、不算填数，
  引擎也完全不看它。
- 一局记录三件事：步数（你自己写的每一笔，含笔记）、提示次数、用时。成绩排名先比提示，
  再比步数，最后比用时 —— 求助不该比硬推更好看。
- 关掉页面再回来，存档会把你放回**同一局的同一盘面**（种子 + 墨水 + 笔记），不是重开一局。

## 六条规则（提示只会说这些）

提示不会给你「答案」，它只会把某一条规则**说出来并指出格子**。三档共用同一套规则，
分数就是这些规则的加权出手数。

| 规则 | 权重 | 什么时候成立 | 提示会说 |
| --- | --- | --- | --- |
| 行列补全 | 1 | 一行/列只差一格：M 减已和就是它。或者一个数在**全盘**只剩一格放得下 | `第2行只差一格：M=15 减已和 6 = 9，所以 第2行第2列 = 9` |
| 候选排除 | 1.5 | 某格的候选被线里的已用数挤到只剩一个 | `第1行第3列的候选只剩 4：…` |
| 对角线 | 2 | 同上两条，但用对角线/斜带（泛对角档还吃 8 条斜带） | `主对角线只差一格…` / `右斜带 1 里 7 只剩一格放得下…` |
| 区间剪枝 | 2.5 | 用「这条线剩下的格必须凑出 deficits」剪掉不可能的取值（区间上下界） | `第3行第1列不能是 8：那一行剩下的两格要凑到 20…` |
| 互补对称 | 3 | 中心对称的两格之和等于 n²+1（九宫：对面 = 10 − 这格） | `九宫中心对称的两格和为 10：…` |
| 反证 | 6 | 假设某格取某值后整盘推不倒（深度 1 的反证），排除掉它 | `若 第1行第1列 = 2 会推不出任何一步，所以不是它` |

两个诚实的边界：

- **互补对称只在九宫给得出。** 它不是「看起来对称」的口味，是数出来的：三阶的 8 个盘
  **8/8 都满足**中心对称互补（因为中心只能是 5）；四阶普通幻方里只有 **384/7040** 满足（5.5%）；
  而四阶泛对角盘里 **384 个中有 0 个**满足 —— 这类盘里根本不存在互补对称的。所以四四/泛对角
  档的规则表里把它关掉（`ASSOCIATED = {'3:plain':true,'4:plain':false,'4:pan':false}`，
  两个数都是 `npm test` 现场算的，见上）。
- **反证在出货的局里出手 0 次**（下表实测）。这是设计而非巧合：反证权重最高（6），
  真需要它才推不动的盘会被筛子挡在区间外。它留在引擎里，是为了让「推不动」这件事
  有一个可测量的定义，而不是为了让提示显得高深。

## 难度是量出来的

`npm run balance` 的实测输出（三档各抽 40 局，本机 2026-09-27）：

| 档位 | 线索 | 目标区间 | 出货 | 命中区间 | 分数中位（p25/p75/max） | 步数中位 | 规则出手（补全·排除·剪枝·对角·对称·反证） | ms/局 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 九宫 3×3 | 4 | 8–20 | 40/40 | 40/40 | **13.0**（12.0 / 13.0 / 13.0） | 7 | 130·0·80·48·22·**0** | 1 |
| 四四 4×4 | 7 | 90–130 | 40/40 | 40/40 | **109.5**（102.5 / 118.5 / 129.5） | 49 | 278·55·1480·176·0·**0** | 6 |
| 泛对角 4×4 | 6 | 132–170 | 40/40 | 40/40 | **154.5**（141.5 / 163.0 / 170.0） | 70 | 268·52·1699·759·0·**0** | 30 |

平均抽卡次数 2.1 / 1.9 / 1.4 —— 抽不满是因为筛得严，不是因为筛得松。
三档的中位分数单调递增（13.0 < 109.5 < 154.5），且**每一局**都落在自己区间内，
所以「泛对角比四四难」这句话是量出来的，不是文案写的。

表里只有最后一列（ms/局）是机器相关的：换一台机器、关掉后台进程都能让它浮动一倍。
其余每一列都由种子决定，`npm run balance` 在任何机器上重跑都应给出同样的分数与计数
—— 复现命令见 DESIGN.md 「复现这些数字」。

同一轮里另外三组交叉验证：

- **裸分布**（band 不参与挑选，`tries=1` 一张一张看）：九宫 min 5 / med 13 / max 42，
  四四 90.5 / 104 / 141.5，泛对角 123 / 159.5 / 186.5；出货率 12/12 每档，推不尽 0，多解 0。
- **穷举复核**：18/18 局用第二套实现逐格比对，解答一致；三档复解一致 3/3；
  抽盘器给出的正解自身合法 40/40。
- **线索下界**：九宫出货盘删到中位 2 条线索仍唯一，四四 4，泛对角 3，截断 0/8。
  也就是说留 4/7/6 条线索是有余地的，不是把唯一解逼到悬崖边。

`npm test` 的穷举清点（同一轮里现场跑，节点数是真的 DFS 节点数）：

| 类别 | 全盘数 | 去 D₄ 对称后的基本盘 | Burnside 独立给出 | 搜索节点 |
| --- | --- | --- | --- | --- |
| 三阶 | 8 | 1（8/8） | 1（不动点和 = 8） | 58 |
| 四阶 | 7040 | 880（7040/8） | 880（不动点和 = 7040） | 1,662,753 |
| 四阶泛对角 | 384 | 48（384/8） | 48 | 1,537,937 |

三条轨道计数都满足 `total / 8 == fundamental`，Burnside 的另一条路（按 8 个对称求不动点和）
也给出同一个数，所以 D₄ 作用是自由的 —— 没有盘被自己的对称「按住」。

M = n(n²+1)/2 在 n=1..8 上给 1, 5, 15, 34, 65, 111, 175, 260；本作只出 n=3 与 n=4。
